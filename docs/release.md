# Release process

Status: **written, never run.** No release has been made, no tag exists, and `release.yml` has not run on GitHub yet.

## What a release contains (per `release.yml`)
For each ABI (arm64-v8a, armeabi-v7a, x86, x86_64; owner decision D21) one debug APK and one release APK, named
`viddown-<version>-<debug|release>-<abi>[-UNSIGNED].apk`, plus:

| file | purpose |
|---|---|
| `SHA256SUMS.txt` | SHA-256 of every other file in the release (calculated in the workflow) |
| `BUILD_INFO.app.json` | version, app commit, workflow run URL, whether the release APK is signed, ABIs built |
| `BUILD_INFO.native.json` | the exact release tag and commits of each tool (yt-dlp, cpython, ffmpeg) and the SHA-256 of every zip, produced by `scripts/fetch_native_bundle.py` |
| `test-and-lint-reports.zip` | JUnit XML and lint reports of the unit-test + lint run that preceded the build (`scripts/collect_reports.py` fails when there are none) |
| `RELEASE_NOTES.md` | generated by `scripts/release_notes.py`; every ABI without a PASS runtime check is labelled NOT VERIFIED |

Build logs: on a failed run the job uploads `failure-reports` (Gradle reports); the full log is the Actions run itself.
**No AAB** (decision D85): an AAB would deliver every ABI's runtime to every device and cannot carry the per-ABI verification labels. Revisit only after ABIs are verified.
**No GitHub build attestation** (decision D86): it needs extra permissions (`id-token`, `attestations`) and is not available for every repository plan; provenance is the BUILD_INFO files + SHA256SUMS. Add it later if the repository supports it.

## Changing the version
The version lives in one file: `version.properties` in the repository root.
```
VERSION_NAME=0.1.0   # what people see (About, APK name)
VERSION_CODE=2       # a whole number; must go up with every build installed over an older one
```
Edit the two lines by hand, or run `python3 scripts/set_version.py 0.1.0` (name set, code + 1), `python3 scripts/set_version.py 0.1.0 --code 7`, or `python3 scripts/set_version.py --bump`. Without arguments the script prints the current version.
Do this and commit it **before** tagging: the release tag (`v0.1.0`) names the files, `version.properties` is what the APK itself reports in About, so keep the two equal. A single build can override the file with `-PversionName=... -PversionCode=...`.

## Steps
1. Make sure `ci` is green on the commit and (before claiming any ABI) `poc-runtime-tests` is green. Record verified ABIs in `native/bundle.lock.json` by hand (see `docs/native-bundle.md` section 8); never edit it to make a release look better.
2. Optional signing: create the four repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. All four or none. Without them the release APKs are built **UNSIGNED**, named `-UNSIGNED`, and the notes say so. Never commit a keystore.
3. Set the version (see above) and commit it. Then start the release: push a tag `vX.Y.Z` (`git tag vX.Y.Z && git push origin vX.Y.Z`) or run `release` manually and give the version.
4. The workflow runs unit tests and lint, builds the APKs, writes the metadata and creates a **draft pre-release**. Nothing is published automatically; ordinary commits never trigger it.
5. Review the draft: download, compare `sha256sum -c SHA256SUMS.txt`, read the notes (ABIs NOT VERIFIED, UNSIGNED). Install on a device you own.
6. Only a person presses **Publish**. An unsigned release must not be described as a signed production release.

## When a step fails
* Tests or lint fail: no APK is built; read the `failure-reports` artifact and fix the cause (never skip or weaken tests).
* Bundle fetch or SHA-256 mismatch: the build stops (no fallback source exists by design); run `native-health` and read `docs/native-bundle.md`.
* Wrong release made: delete the draft and the tag; nothing else depends on them.
